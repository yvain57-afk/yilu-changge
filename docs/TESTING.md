# iPhone 优先的精简测试流程

2026-10-12 起按用户要求采用。先在现有 TestFlight 游戏上验证操作、声音、流畅度和存档，再决定微信小游戏接入。iPhone 原生测试能验证共同玩法和触控体验；微信版本接入后仍需在微信内验证加载、性能、生命周期和平台接口。

## 日常只走一个短循环

1. 确定一个具体问题和复现场景。先读当前相关代码/结果；没有新证据，不重新研究全仓和全部历史交付。
2. 小范围修改后只运行相关现有测试。修改 TypeScript 时另跑一次 `npm run typecheck`；文案、说明文档和纯图片替换不默认触发全部代码测试。
3. 只有需要观察新代码时才构建 iPhone 开发版。同一批修改合并构建一次，复用当前开发输出和增量缓存；不同时构建 Web、模拟器、iOS、微信四套。源码未变、已有可用同源构建时直接复测。
4. 手机上复测受影响的真实场景，通常约 5 分钟；出现问题就记录并修复，不用通关全部 20 关证明一个按钮或一个音效。没有问题后结束本轮。

未连接手机或没有新构建时，先完成代码相关检查，明确标记“真机待测”，不启动长录像作为替代。使用现有 TestFlight 版本检查当前体验，无需为了测现状重新编译或上传。更新后先回读手机上实际版本；使用同 bundle 的正常更新，保留原存档。

## 检查命令

```sh
# 22 项短检查：存档/结算、战斗反馈、音乐状态；串行执行，不构建、不录像。
npm run check:fast

# 实际修改哪个模块，就选择相关文件；一次传入多个文件即可。
npm run test:targeted -- tests/campaign20-store.test.ts
npm run test:targeted -- tests/combat-feedback.test.ts tests/weapon-sfx.test.ts
npm run test:targeted -- tests/music-shanhe.test.ts

# TypeScript 改动时使用，不作为每次手机重试的必需步骤。
npm run typecheck

# 大范围规则/存档迁移/战斗共享流程变动、正式候选或相关失败时扩大检查。
npm run check:full
```

`test:targeted` 必须指定真实测试文件；空参数或错误文件会退出，不会隐式启动全量。`check:fast` 是固定的少量检查，不代表全面验收；音频单元测试通过也不代表 iPhone 实际发声。`npm test` 与历史专项脚本仍保留，按改动需要选用。既有失败和明确的必要验收不能因流程简化改成通过。

## 第一轮 iPhone 短测

先使用手机现有 TestFlight 版本，不要求清档或解锁测试关卡。

| 场景 | 要确认的结果 |
| --- | --- |
| 首页到整备再开战 | 可点击、无裁切，返回正常 |
| 一场当前能进入的普通战斗 | 左右拖动跟手，敌将预警看得清；胜负与结算正常 |
| 当前进度允许时，兵力较多或连弩战斗 | 是否持续卡顿、发热；若未到该进度，留待后续自然解锁 |
| 音乐/音效开关、战斗与菜单切换 | 实际听到声音，开关有效，无重叠播放 |
| 切后台约 10 秒再回来，随后退出重开 | 恢复正常，进度和编组保留 |

实际时长以完成受影响场景为准，5 分钟是日常目标，不是强制缩短必要验收。只需记录“手机型号、iOS、游戏版本、场景、问题/通过”。体验描述与实测 FPS 分开；无测量时不声称达到 60 FPS。优化优先处理可复现的触控、音频和卡顿问题，保留已认可的画面与玩法方向。

## 控制时间、算力和空间

- 普通一轮默认零录像，最多 2 张有用截图和一段简短结果；只有动作/声音问题需要证据时录 20–30 秒片段。新日常测试产物以 20 MB 内为目标，超出时按诊断需要保留，不做静默删除。
- 日常复测不运行长时间自动通关、全角色组合、逐帧大 JSON、多套浏览器和重复双审。只有具体风险或正式候选需要时启用相关专项。
- 不每次复制工程树、制作源码 ZIP 或重新导出整套素材；用源文件差异、小型记录和现有恢复资料。
- 新日常临时产物统一在 `.cache/iphone-quick/`；新一轮只替换已确认无用的本流程临时文件。有诊断价值的失败记录先保留。
- 当前可用构建、必要上一版、发布 dSYM、源码与独有素材继续保留。重建成本高的增量缓存继续复用；只退役确认可重建且不再使用的中间件，不按目录名含 cache 或日期旧就删除。
- 正式候选再做跨模块检查及平台专项；微信接入后的手机微信实测单独完成，不把 iOS 结果当成微信验收。
